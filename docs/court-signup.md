# 活动内按场地与时段接龙

活动页面的「添加场地 / 时段」可设置球馆、场地、开始和结束、接龙上限、费用。时间选择仍为整点与半点。追加超出原时间的预约会扩展活动起止时间，报名截止需按实际安排由创建者调整。

每个预约有独立正式名单、候补顺序、取消申请和自动递补。成员可报多个不重叠时段，首尾相接允许；本人、自己代报的朋友、活动创建者和管理员沿用原权限。取消本场须提前至少 24 小时，逾期保留名额并申请处理。场地设置不能降低至正式人数以下或裁掉现有报名时段。

## 存储及兼容

- `Booking.signupCapacity` 为本场上限，缺省使用活动原上限；`venue/address` 可覆盖活动球馆。
- `Registration` 保持每活动每球友一条，新增可选 `bookingSignups`，每条含预约 ID、正式/候补/取消状态、序号、参加区间、报名和递补时间、备注、取消申请。活动总状态从各场派生，人数按球友去重。
- `Attendance.bookingId` 保留取消或调整前已发生的场地参加区间。自动参加采用正式时段的并集，空档不参加，迟报名和递补不追溯计费。
- 数据存于现有 D1 表的 JSON payload，经参数绑定与 revision 唯一事务门保存；未改 SQL 表结构，不需要迁移。POST 的 `courtRegister/courtCancel` 进入已有并发重试和请求幂等流程。
- 活动页只展示场地接龙。2026-10-05 按群主要求，将同日两场未开始活动合并，原报名按各自唯一的场地预约迁入，保留序号、备注、正式/候补、报名和递补时间。原来源活动保留可恢复备份。已有附加费用、不同费用模式、既有结算和已进行比赛不参与合并；原来源预排与比赛也完整保留在备份内。

## 分组和费用

场地报名者只能排入对应正式报名的完整时段。每个场地至少四位可参加球友才能排双打；交换、移场、发布、开赛和固定搭档均校验该约束。未指定场地的旧接龙沿用原轮转安排。

场地费在该场参加者之间按活动选择的均摊、时长或逐时段方式分配；球费和其他费沿用活动口径，豁免、群补贴、未分配和逐分对账保留。球友报名多个场地的非连续时段不会把中间空档计为参加。

## 验证

`node scripts/test.mjs` 包含 `tests/court-signup.test.ts`：独立名额与递补、重复保存、时间冲突、取消归档、逾期取消权限、三种场费模式、双打/固定搭档、场地编辑、旧记录转换与 JSON 重读。

另在隔离本地 Worker + D1 的虚构数据中验证两请求同时争抢最后名额（一个正式、一个候补）、相同 requestId 幂等、只取消一个场地并独立递补，以及重新读取已保存名单。预览数据和工具脚本均在忽略目录，未进入发布包。

## 已完成的活动数据迁移

2026-10-05 已核对线上只保留一个活动：10月10日 1号场 15:00–17:00（4人），2号场 15:00–19:00（5人），各上限6人。9条报名的参加时间、序号、备注、正式状态、报名时间和取消申请均与迁移前一致。原活动链接指向合并后的活动，来源记录留作可恢复备份。

迁移使用固定操作账本和 revision 事务门，拒绝重复执行，不接受访问者参数。核对成功后已移除首页执行钩子，正常访问不会再执行数据迁移；实现和测试保留用于审计。
