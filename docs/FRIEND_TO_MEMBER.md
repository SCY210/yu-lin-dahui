# 临时来宾转为正式成员

成员带来的朋友是临时来宾（[GUEST_FRIENDS.md](GUEST_FRIENDS.md)），每场活动各有一条记录，没有球员档案、修为或积分。朋友以后想自己登录时，管理员在创建账号时把这位朋友转为正式成员。

## 创建账号时的球友档案下拉框

`app/account-manager.tsx` 的"球友档案"列出三类选项：

- **创建新球友档案**：从零开始。
- **某某 · 保留历史记录**：没有账号的成员档案（不是临时来宾），例如以前的成员档案。新账号直接接管这份档案。
- **某某（带来人 的朋友）· 转为正式成员**：每位朋友一行，和"临时来宾"名单用同一份分组（`accountProfileChoices` 调用 `recordedFriends`，都在 `lib/client/recorded-friends.ts`）：合并过的朋友只算一位，移出名单的不列。选中后昵称可以改成本人的名字，下面会提示这位朋友参加过几场活动。

以前下拉框只列早期"代朋友接龙"留下的旧朋友记录，而且每条记录单独一行，所以同一位朋友会出现好几次，合并或移出名单的也照样列出；按活动建的朋友则一个都不列，和"临时来宾"名单对不上。

## 转换做了什么

服务端在 `createAccount`（`app/api/auth/route.ts`）里发现选中的是临时来宾，就调用 `convertFriendToMember`（`lib/domain/guest-conversion.ts`），在同一个事务里：

1. 找出这位朋友的全部记录（`friendRecords`）。选中的那条留下来，作为新成员的球员记录。
2. 把其他记录在所有地方的引用都改成这条：接龙、比赛、轮次、到场、投票、费用分摊和付款等。审计日志保持原样，不改写历史。
3. 删除被合并的记录，新成员不再带 `guestEventId`、`guestFriendId`、`guestLevels` 和"移出名单"标记；性别保留，用于搭配。
4. 新成员的初始修为是朋友最后一次设定的水平，再按正式成员重放全部比赛，所以过去的比赛会计入新成员的修为和积分。
5. 审计记录 `createLoginAccount` 写明"临时来宾转为正式成员"，以及合并前每条记录的名字、带来人、活动和水平，被合并和被留下的记录 ID。

数据库会先删掉被移除的行，再写入改动的行；被合并的记录在改写前还被旧接龙引用，所以它们放在同一批写入的最后删除。

## 不能转换的情况

- 这位朋友在同一场活动里有两条有效接龙（以前重复接龙留下的）：转换会让新成员在那场活动里出现两次，所以拒绝，提示先在"临时来宾"的"同一场活动里重复的接龙"里取消多余的那条。取消后，那条只剩已取消接龙、也没打过比赛的记录不会被合并，而是留作移出名单的临时来宾记录，历史不删；其余记录照常并到新成员。下拉框选中的正好是这条时，改由最新的另一条记录承接新成员。
- 同一位朋友的两条记录出现在同一处其他数据里：同样拒绝，不改任何数据。
- 只有管理员能创建账号；已经有账号的档案不能再被接管。

## 验证

`tests/guest-conversion.test.ts` 覆盖合并后的接龙、比赛、修为重放、审计不变，以及同一场活动两条接龙时拒绝且数据不变、取消重复接龙后那条留下而其余照常转换。`tests/account-profile-choices.test.ts` 覆盖下拉框：旧记录同一位朋友只列一次、按活动建的朋友也列出、移出名单的不列、朋友不当作成员档案。`tests/friend-to-member-api.mjs` 走真实的账号接口和事务存储：只有管理员能做、所有记录并到新成员、登录可用、重试不重复创建、同一档案不能被接管两次。
