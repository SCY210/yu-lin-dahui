# Personal score entry on app return

Opening the authenticated app or returning it to the foreground directly opens the score form for the account's own started, still-playing game. There is no preliminary "finished?" confirmation screen. The default form has only two large numeric inputs and a submit button. The member's own team is first and receives initial input focus, even when it is stored as side B; submission retains the original A/B mapping. Actual team names and the activity/court remain visible. The member can postpone entry, and a compact banner provides direct manual access.

Eligibility uses the existing, authorized club projection and existing `canRecordScore` policy. The current account's enabled player must appear on one team, with a started non-future match, its playing parent round and a visible non-deleted activity. Draft/cancelled activities, finished/voided games and unrelated/proxy games are excluded. Administrator access to another player's game does not make it that administrator's personal reminder. Activity ending does not silently discard an otherwise recordable pending result. The newest pending game is offered first; older pending games can be selected.

The initial visit is consumed even if there are no pending games. Ordinary polling and automatic live assignments therefore never continually reopen score entry. A return to the foreground refreshes shared state before arming another visit. Existing forms, dialogs, pending writes and connection errors defer the prompt. A score draft already open is preserved on foreground return. Closing/postponing consumes that visit; manual access remains available. Account changes remount the reminder and stale asynchronous responses cannot arm it for another account. A voided selected game disappears; a remotely completed selected game stays open for explicit confirmation or correction.

Score submission uses the original optimistic, idempotent API, so server permission, revision, score validation and live-court progression still apply. No completion is stored without confirmation of actual scores. First entry supplies the existing standard audit reason without asking the member to type it. Historical corrections also use an automatic operation description and do not require user prose. Scoring explanations are omitted from the initial form; best-of-three and alternate pending games are optional collapsed sections. Unrecorded games stay blank, clearing an input keeps it blank, and additional games never insert invented results. New completions use server time; corrections retain the exact original timestamp.

No schema migration, background phone notification or new scoring permission is introduced. The banner is separate from the existing activity notification center.

Tests cover personal participation, proxy/admin separation, permissions, activity/round visibility, future and completed records, ordering, one form per visit, empty initial visits, blocking/postponement, foreground response races and blank drafts. Headless React tests exercise direct initial form entry, exactly two numeric inputs, absence of the reason field, autofocus, postpone/manual access, empty-submit rejection, clearing/editing, successful completion, no immediate next-game popup, foreground return and side-B display/submission mapping. Dialog shells substitute for browser portals; actual mobile layout remains a device verification. The fixture is under tests and never a published route. Original scoring/live-play API tests remain in regression validation.

## Face-off form and simultaneous entry

The form has no explanatory text. The two teams face each other with avatars and names, the viewer's own team on the left, and one score box sits under each team. The court and activity name are the only context line.

Several players often score the same game at once. The form sends the games it opened with (`expectedGames`, empty for an unscored game) together with the lineup snapshot. The server then accepts an unchanged match normally. It accepts the same score arriving from a second phone without changing anything. It refuses a different score with 409, naming who entered which score (`lib/domain/score-conflict.ts`). A score carrying these snapshots is guarded by the match itself, so it no longer fails because another court saved a score first (`lib/lineup-write.ts`). If another player's score arrives while the form is open, the form shows that score instead of the inputs, with a button to accept it (close) and one to correct it (reopen as a correction prefilled with the saved score). The projection adds `enteredByPlayerId` to matches so members can see who saved a score without seeing accounts.

Identical concurrent results do not create an extra score audit. Account and activity permissions still run before that no-op path; request IDs retain their normal authenticated retry semantics.

Tests: `tests/score-conflict.test.ts`, `tests/lineup-sync.test.ts`, `tests/score-conflict-api.mjs` and `tests/score-conflict-ui.mjs`. The API suite uses actual handlers and transactional SQLite for independent courts, same-match conflicts, duplicate results, permission refusal, immutable retries and rollback. The UI suite retains a remotely completed dialog and verifies explicit correction with the displayed side-B-first order.

Long player names wrap to two lines in the score form and in the phone court cards (breaking inside long Latin names) before an ellipsis; the profile and the button title keep the full name.
